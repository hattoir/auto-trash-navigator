タスク2: 接近しながらの目標更新(本命)
  src/amr_bringup/scripts/patrol_and_collect.py を改修。

  1. 定数追加:
     RETARGET_GATE_DIST = 0.5   (現在の追跡対象からこの距離以内のみ採用)
     RETARGET_MIN_MOVE  = 0.02  (これ未満の移動はノイズとして無視)
     MAX_TARGET_UPDATES = 3     (1回の接近あたりの更新上限)

  2. trash_callback() に APPROACH状態専用の分岐を追加。
     従来は state != 'PATROL' のとき即return していたが、
     state == 'APPROACH' かつ current_target_trash が設定済みのときは、
     新規検出座標と現在の追跡対象との距離dを計算し、
       RETARGET_MIN_MOVE < d < RETARGET_GATE_DIST
       かつ target_update_count < MAX_TARGET_UPDATES
     を満たす場合のみ current_target_trash を新座標へ更新し、
     target_update_pending フラグを立てる。更新のたびに
     「旧座標→新座標、移動量d、更新回数/上限」をログ出力する。
     距離ゲート必須により別のゴミへの誤乗り換えを防止。
     ranging_mode('depth'/'mono')による分岐は一切なし
     (/detected_trash に来た座標に対して汎用的に反応する設計のため、
     このロジックは検出器の種類を問わない)。

  3. APPROACH状態のゴール送信ループ(isTaskComplete()ポーリング内)で
     target_update_pending を検知したら:
       - navigator.cancelTask() で現在のNav2ゴールをキャンセル
       - キャンセル完了を待つ
       - 更新後の current_target_trash から
         compute_approach_goal()(既存の接近オフセット計算を
         関数化しただけで数式・IK回避オフセットは無変更)で
         ゴールを再計算し、goToPose()で再送
       - 90秒タイムアウトのカウンタをリセット
     この処理を1回の接近試行(attempt)内で繰り返し、
     成功/失敗判定・COLLECT状態への遷移・ブラックリスト登録は
     すべて「最終的に更新されたtx,ty」を使うよう自然に連動する
     (変数を使い回しているため追加のコード分岐は不要)。

     接近開始時(APPROACH状態の先頭)で
     target_update_count / target_update_pending を毎回0/Falseに
     リセットするので、更新上限は「1件のゴミへの接近ごと」に適用される。

  4. 変更していないもの(指示通り):
     depth_trash_detector.py, mono_ranging.py の測距ロジック、
     6条件の判定基準そのもの、main() の骨格(状態遷移PATROL→APPROACH→
     COLLECT→PATROL)、COLLECT状態のリトライ・調整ロジック、
     PATROL状態のロジック。

  (b) 回収時ロボット↔対象1.0m以内
      -> 合格(接近完了時の実測距離: 0.355m/0.358m/0.332m、いずれも1.0m未満)
  (c) 回収後2周以上の巡回継続
      -> 合格(3件目回収(t=1180s)後、20分打ち切り(t=1214s)まで
         約34秒しか無いように見えるが、これは3件目が試験の後半

         から数えると約267秒で3周以上を消化しており、3件目回収後も
         WP3→WP1→WP2 の遷移が20分打ち切り時点で継続中(打ち切りは
         時間経過によるものであり、巡回停止によるものではない)。
         ログ上、State TransitionのPATROL遷移は全体で57回あり、
         打ち切りまで異常終了なく周回し続けたことを確認)
  (d) patrol生存・z<0.1
      -> 合格(gz実測 z=0.000、エラー/シャットダウンログなし)
  (e) WP圏実周回
      -> 合格(WP1→WP2→WP3の順で規則的に遷移し続けた)
  (f) 再回収なし
      -> 合格(回収完了ログは id=1,2,3 の3回のみ。processed_trash/
         blacklisted_trash による重複防止ロジックは無変更)

  総合判定: 6条件すべて合格。目標更新ロジック導入による退行なし。

■ 目標更新の発火統計

  ログ中の "Target Update #" 出現回数: 0回
  接近3回(Trash ID 1,2,3)すべてで目標更新は発火しなかった。

  想定通りの結果: ranging_mode='depth' はsimの深度画像から直接測距しており
  (誤差2〜4cm程度)、そもそも初回検出座標と接近中の再検出座標の差が
  RETARGET_MIN_MOVE(2cm)を上回るほどブレないため、更新ロジックが
  発火する場面がほとんど無い。これは「壊れていない」ことの証拠であり、
  同時に「深度方式では実害がない(過剰な再計画を起こさない)」という
  タスク要件(5)を満たしていることも示す。
  mono方式での実発火確認は本検証の対象外(タスク指定通り、
  検証1はdepth既定での非退行確認が主目的)。

■ 残った問題

  1. mono_ranging_mode='mono' での目標更新の実発火確認は未実施。
     simのRGBカメラでは紙くずが灰色描画されYOLOが検出できないため
     (既知の制約、CMakeLists.txt/launchのコメントに明記済み)、
     sim環境でmono経路を統合テストすることはそもそもできない。
     実機での検証、または静止画/rosbagでのyolo_trash_detector.py単体
     テストが今後必要(このタスクのスコープ外)。
  2. 条件(c)の「2周以上」は3件目回収がテスト後半に発生したため、
     3件目回収後の周回時間が短く見える。1件目回収後を起点にすれば
     3周以上を消化しているが、要求文言の解釈次第では3件目回収後
     単独で2周に満たない可能性がある(打ち切りが時間経過によるもので
     巡回停止によるものではないことは確認済み)。より長い無介入時間
     (例: 25分)で3件目回収後の周回数を明示的に確保する再検証が
     望ましい場合、別途実施を検討のこと。
  3. pick_and_place.py の "IK failed with error code: -31" 警告は
     従来から出ている既知のログ(探索過程での試行錯誤、最終的には
     成功しているため実害なし)。今回の変更とは無関係。

## 7/13 深度検出器を書いた。そして動かなかった

色が使えないので深度で拾う方式に切り替えた。原理はシンプルで、「床は平らなはずなのに、そこだけ数センチ盛り上がっている小さな塊」を探すだけ。色にも照明にも依存しないから、こっちのほうが本当は筋がいい。

書いて、起動して、巡回させた。8周した。検出ゼロ。

原因はフレーム名だった。Gazeboが吐く深度画像のframe_idが `visual_amr/base_footprint/oakd_camera` というGazebo内部の名前で、TFツリーにはそんなフレームは存在しない。検出器は毎フレーム座標変換に失敗し続けていた。ログには警告が出ていたけど、監視のgrepパターンに入れていなかったから気づかなかった。自分の見張りの網の目が粗かっただけ。

`optical_frame` を明示指定して変換は通るようになった。それでも検出されない。

そこで、深度画像から床の平面をフィットしてカメラの高さと角度を逆算する計算を書いて回してみた。

```
カメラ高さ h=0.480m / ピッチ 13.1度
(設計値は h=0.200m / 15度)
```

角度は合ってる。高さが28cm多い。**カメラが浮いている。**

## 7/16 ロボットが浮いていた

`gz model -m visual_amr -p` で見たら z=0.274。27cm浮いている。しかも毎秒1mmずつ上昇し続けている。熱気球か。

一度 set_pose で床に置き直すと落ち着くが、放っておくとまたじわじわ上がる。関節の角度を2回測ってみたけどアームは全部ゼロで不動。アームが竹馬になって車体を持ち上げている説は消えた。

犯人は **DetachableJoint** だった。gz-simのこのプラグインは、**起動した瞬間から「接続済み」で始まる**仕様だった。つまりシミュレーション開始の0秒から、アーム先端と紙くず3個が見えないゴムひもで繋がったままだった。ロボットが巡回で離れるたび、物理エンジンが拘束を満たそうと力をかけ続ける。それが車体をゆっくり持ち上げていた。

3本のdetachを手で打った瞬間、z=-0.000002。2分間ぴくりとも動かない。

これで説明がついたものが3つある。

1. 車体の浮上
2. 紙くずが誰にも触られていないのに2cmずれていた件
3. 経路計画が周期的に「Failed to create plan」で失敗していた件

無関係に見えた3つの怪現象が、全部ひとつの原因から出ていた。こういうのは気持ちがいい。

## 7/17 検出器を自己較正方式に書き直した

浮きの件で分かったのは、「URDFに書いてある高さ」と「実際にそこにある高さ」は別物だということ。じゃあTFを信じるのをやめよう、と思って検出器を書き直した。

毎フレーム、深度画像そのものから床の平面をフィットして、そのフィットした床を基準に「浮いている塊」を探す。カメラの取り付け位置がズレていようが、車体が浮いていようが、実機に載せ替えて車高が変わろうが狂わない。

ついでにGPUの話。今この環境はGazeboもRVizも `llvmpipe`(CPUで3D描画するソフトウェア)で動いている。Phase 2のときにGazebo GUIが起動即クラッシュしたのを回避するために入れた対策で、それ自体は正しい判断だったけど、利子がずっと付いてきている。RTFの低下も、RGBが灰色になるのも、全部この回避策の副作用圏内。GPU自体は計算(CUDA)には使えるはずなので、描画(OpenGL)の配線だけが切れている状態だと思う。**直すのは完成後**。今いじるとGazeboごと起動しなくなるリスクがある。

## 7/20 幻影を追いかけていた

検出座標をちゃんと見たら、こんなのが出ていた。

```
Published /detected_trash map:(-4.79,-0.23)  area=519px
Published /detected_trash map:(-5.50,-1.76)  area=536px
```

部屋は±4mなのに、地図の外。しかも面積500px超。紙くず(直径24mm)なら1.5mの距離で40pxくらいのはずで、桁が違う。**壁の根元を拾っていた。** 3m先だと床面フィットのわずかな角度誤差が拡大して、壁の付け根の帯が「床から数cm浮いた塊」の判定に入り込む。

ロボットはその幻影に向かって走り、部屋の外へ経路を引こうとして失敗し続けていた。

フィルタを4枚重ねた。検出距離を2.5mまで、面積上限400px、横幅0.15m超は棄却(壁は横に何mも続くので確実に落ちる)、地図の外の座標は無条件棄却。

そしてもう一つ、もっと悪いものが見つかった。**DetachableJointのattachは距離に関係なく成立する。** ロボットが幻影の座標に着いてattachを打つと、1m以上離れた本物の紙くずと車体が繋がって、そのまま引きずり回して、detachで放り出す。前に紙くずが部屋の隅まで5.7m飛んでいた謎の答えがこれだった。

対策として、既知の紙くず位置から0.5m以上離れた検出は無視する、ピック直前にロボットと目標の実距離が0.8m以内でなければattachを打たない、という二重のゲートを入れた。

## 7/24 監査の日(この日が一番長かった)

### 午前: agyの報告を疑う

agyから「統合テスト合格、すべての課題が完璧に解消」という報告が来た。読んでいくと変だった。

- 「合格」と言っているのに、回収完了は **1件**(条件は3件)
- 「クリーンに正常終了」と書いてあるが、patrolは無限に巡回する設計。終了するのは安全装置が働いたときだけ
- ドロップ先が、元の位置の30cm隣
- **paper_1とpaper_3がどうなったのか、一言も書いていない**

依頼していない変更も5件以上入っていた。ここで、実装しているエージェントに自己採点させるのをやめて、**別のAI(Claude Code)に独立監査人として入ってもらう**ことにした。実装権限なし、介入なし、生の数字だけ報告させる。

### 午後: 監査の結果

クリーンな環境で20分回した結果。

- 回収 **0件**
- 紙くず3個は19分間、1ミリも動いていない
- patrolは18分18秒で航法失敗の連鎖により自己終了
- ロボットの実体は、20分間ずっと左上のコーナー(-3.7, 3.6)に張り付いていた。**なのにログは「WP到達成功」を12回記録していた**

さらに監査人は、**コミット済みのコードから構造欠陥を3つ**掘り出した。

1. リトライループのインデントがずれていて、2回試すはずが実質1回しか試していない
2. 回収成功時の `break` が、メインの `while` を抜けていた。つまり**設計上、1個拾ったらプログラムが終了する構造**だった。「3個回収して2周巡回」はコードの構造として最初から不可能だった
3. 検出の受理半径0.5m と ピックの拒否閾値0.3m が不整合。0.3〜0.5mの誤差で検出したゴミは、必ず拒否される

3つとも、今まで「たまたま発火しなかっただけ」の地雷だった。

### 夕方: 真犯人

構造欠陥を直しても、ロボットはコーナーに張り付いたままだった。「実体はここにいるのに、自己位置は部屋を回っていると思っている」という乖離が残っている。

TFの二重配信を疑った(過去に踏んだ罠)。シロ。map→odom を配っているのはAMCLだけで、ツリーは健全だった。

じゃあということで、Nav2を全部止めて、Gazeboだけで開ループの真値試験をやった。`/cmd_vel` に +x を3秒送って、実際にどっちへ何m動くかを測るだけ。

```
+x 0.2m/s 3秒 → 実測 x: -0.628
+y 0.2m/s 3秒 → 実測 y: -0.795
+yaw 0.5rad/s → 実測 yaw: -2.450
```

**3軸すべて逆。** そして `/odom` を見ると、真値のちょうど符号を反転した値を報告していた。

つまりこういうことだった。Nav2が「前へ」と指令する → 機体は物理的に後ろへ走る → オドメトリは「前へ進みました」と報告する → EKFとAMCLはそれを信じて自己位置を前へ進める → 「WP到達成功」のログが出る → 実体は壁に押し付けられている。

原因は `base_omni_4wheel.xacro` の車輪ジョイントの軸、たった1行。

```xml
<axis xyz="0 -1 0"/>  →  <axis xyz="0 1 0"/>
```

マイナス1文字。これで駆動もオドメトリも自己位置も航法も検出も、全部が初めてまともに動き出した。

思い返すと、過去にagyから来た「開ループ真値検証、合格」「5周巡回でAMCL誤差0.3m以内」という報告は、少なくともこの反転がある状態では成立しえない。あれも嘘だったんだと思う。

### 夜: run 4 → run 5 → run 6

**run 4** — 初めてpatrolが20分間死なずに完走した。約24周。Recovery 0、航法失敗 0。回収2/3。残る問題は紙くずの物理だけになった。巡回経路の7cm横にスポーンしていたtrash_3が轢かれて弾き飛ばされる。そして一度動いた10gの球が減衰せず、20分間ずっと部屋の外周を滑走し続ける(velocity_decayを入れても効かなかった)。

**run 5** — 紙くずを静的モデル+コリジョン削除にした。深度検出はレンダリングベースなので、collisionが無くても普通に見える。轢かれない、滑らない、弾かれない。結果、**3/3回収を初めて達成**。ただし「初期位置から0.5m以上移動」という条件だけ未達だった。理由は幾何学的なもので、ロボットが対象の0.3mまで寄って拾い、腕の届く位置に置くのだから、移動量は腕のリーチ分(0.17〜0.22m)にしかならない。3件とも同じような値なのが、偶然でない証拠。

**run 6** — 部屋の隅にダストボックス(3.5, -3.5)を置いて、ドロップ先をそこにした。回収したゴミが1箇所に集まる、本来やりたかった形。

```
回収完了 3/3
各回収時のロボット↔対象距離: 0.307m / 0.314m / 0.299m
検出誤差: 0.019m / 0.036m / 0.039m
3個ともダストボックス座標に誤差 0.000m で到達、20分間座標変動ゼロ
回収後 22.7周 巡回、Recovery 0 / 失敗 0 / 再回収 0
patrol 20分完走、車体 z = -0.000
完全無介入
```

**全条件合格。** タグ `project-complete-verified`(a0a1c6e)。

## 7/26 リポジトリの整理

minicar時代の旧mainと、AMRのamr-workspaceに分かれていたのを一本化した。

```
main/
├── src/          amr_bringup / amr_control / amr_description / amr_moveit_config / amr_vision
├── legacy/       COLCON_IGNORE + minicar_simulation
├── 6-arm-roboto/ 実機アームCAD(維持)
```

`legacy/COLCON_IGNORE` を置かないと、colconが旧minicarパッケージを拾ってビルドが壊れる。これは事前に気づけてよかった。

整理のあとにもう一度スモークテストを回して、「回収完了 → 紙くずがダストボックス座標に到達」を確認した。ファイル整理は動くものを壊す典型作業なので、ここでも物理で確かめてから終わりにした。

`launch` が `/home/pakku/...` の絶対パスを直書きしているのは技術的負債。本来 `get_package_share_directory` にすべきだけど、今それをやると検証済みの状態を触ることになるので、READMEの「既知の課題」に書くだけにした。

### 技術的に一番効いた修正(効果の大きい順)

1. **車輪ジョイントの軸極性**(1文字) — 駆動・オドメトリ・自己位置・航法・検出、全系が正常化
2. **DetachableJointの撤去** — 浮上・ドリフト・遠隔吸着・経路計画異常が同時に消滅
3. **回収成功時のbreakスコープ** — 「1個で終了」という設計上の詰みを解消
4. **検出の深度ベース化+自己較正** — 灰色レンダリングを迂回。実機にも持っていける方式
5. **車輪コリジョンを円柱→球**(Phase 1) — メカナムの横行がそもそも成立していなかった問題

### 検証について学んだこと

これが今回いちばん価値のある収穫だと思う。

- **ログは証拠にならない。** 「回収完了」と書いてあるコードが走ったこと以上の意味はない。物が動いたかは `gz model -p` で聞く
- **実装したエージェントに自己採点させない。** 別のAIに監査人として入ってもらい、実装権限を与えず、生の数字だけ出させる。今回それをやって初めて全部が見えた
- **「定義が正しい」と「実行時にそうなっている」は別物。** 開ループの真値試験(指令 → 実際の変位)が最強の診断
- **無関係に見える複数の症状は、単一の原因を疑う価値がある。** DetachableJointも駆動反転も、それぞれ3〜5個の怪現象をまとめて起こしていた
- **切り分けは上流から。** 入力は来ているか → 対象は写っているか → 閾値は妥当か

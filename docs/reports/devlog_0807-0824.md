# 開発日誌 続き(8/7 〜 8/24)

## 8/7 実寸のURDFにしたら、アームが下手になった

Fusion 360から実測値を全部出して、URDFを書き換えた。リンク長、回転軸(Z-X-X-Z-X-Z)、可動域、質量、重心。これまでは全リンクが真上に積み上がっただけの「柱」で、曲がる構造ですらなかった。

書き換えて可達範囲を測り直したら、**前より狭くなった**。

```
旧(仮値)  真下向き x=0.20〜0.35、|y|≦0.25
新(実寸)  真下向き x=0.00〜0.30、|y|≦0.15
```

一瞬「改悪では」と思ったけど、違う。実機のJ2とJ3は±98°しか曲がらない。真上に伸びた状態から床に手を伸ばすには肩を大きく倒すしかなくて、そこが限界になる。**これが実機の正直な性能**で、今まで見ていた数字のほうが嘘だった。

ついでにIKソルバーをKDLからTRAC-IKに替えた。前のマップが「島状」に穴だらけだったのは、単一シードのニュートン法が局所解に落ちていたから。TRAC-IKにしたら決定論的に同じ解集合を返すようになった。

そして pitch=45° が全滅した理由も判明。pitch=145°(内部表記)でJ2=1.648、可動域の上限1.65まで残り0.002rad。**ソルバーの限界ではなく物理の限界**だった。境界を145°と140°の間で正確に検出できていたので、TRAC-IKの信頼性も同時に確認できた。

## 8/7(夜) アームは真正面が苦手だった

混合姿勢(高いところは真下向き、掴む瞬間だけ斜め)で組み直そうとして、**x=0.30, y=0.00 で解が出ない**ことに気づいた。真正面。しかも |y|≦0.04 の帯全体が到達不能で、|y|≧0.06 から急に解ける。

理由を考えて納得した。J1(ベース旋回)が0のまま真正面へ伸ばすと、肩と肘だけで姿勢を作ることになる。可動域±98°では足りない。少し横にずれると**J1が働いて自由度が跳ね上がる**。

つまり今までの設計 —「ゴミに正対して0.30m手前で止まる」— は、**一番苦手な場所に毎回ゴミを置いていた**。

人間もゴミを拾うとき正面に構えない。体を少しずらして利き手側に持ってくる。同じことだった。接近目標を (0.33, 0.09) に変えた。

## 8/8 「1個目だけ成功して、あとは全部失敗する」

接近オフセットを入れて単体テストは14/15まで来た。でも統合すると、**1個目のピックは必ず成功して、2個目以降は座標に関係なく全部90秒タイムアウトで死ぬ**。しかも3回連続で同じパターン。

Nav2の許容誤差を0.05→0.12→0.20と3段階変えても同じ。パラメータの問題じゃない。**最初のピックを境に、何かが不可逆に壊れている**。

ここで待ち方を変えた。これまで検証を投げて何時間も待って1回失敗して終わり、を繰り返していたので、**時間制限つきの自律改善ループ**にした。90分なり120分なりの予算を与えて、その中で「テスト→診断→許可した範囲の修正→再テスト」を自分で回してもらう。変更していい範囲をホワイトリストで縛って、合格基準とテスト条件だけは絶対に触らせない。

これは正解だった。1回の待ち時間が9時間から30分になった。

## 8/10 joint2が可動域の端に張り付いて戻らない

計測で決着がついた。ピック前/直後/2分後を比べたら、RTF・AMCL誤差・スキャンのHzは一時的に悪化しても2分以内に自然回復する。**joint2だけが1.65radに固着したまま回復しない**。

手でhomeコマンドを送っても、8秒与えても、0.25radだけ動かそうとしても動かない。自己干渉チェックは通る。到達可能域のどの点でも、joint2は可動域の上限から0.0005〜0.025radしか余裕がない。

原因はトルクだった。CADの実測値から計算すると:

```
J2より先の質量        598 g
J2からの合成重心距離  226 mm
腕が水平のときのJ2トルク  1.32 N·m

URDFに設定していた effort  0.6 N·m  ← 必要の45%
```

**自重すら支えられない設定**にしていた。僕が「実用0.6程度」というメモをそのまま全関節に入れたのが原因。物理的に誤ったモデルだった。

joint2/3を1.5、joint5を0.9に訂正して解決。

そしてこれは実機の問題でもある。STS3215のストールは1.9N·m。**必要1.32はその70%**で、余裕率1.44倍しかない。しかも把持姿勢は運動学的にJ2を可動域端(≒水平)に追い込むので、**拾うたびに最悪トルク点を通る**。ストールの70%を連続保持したらサーボが焼ける。ハード側にカウンターバランスか先端軽量化か肩の2サーボ化を検討してもらうよう伝えた。

## 8/20 YOLOの1回目は失敗した(mAP 0.36)

実機はYOLOで判別+深度で測距の2段構えにする予定なので、モデルを作り始めた。144枚撮って、自動ラベルのたたき台をそのまま学習に使ったら mAP50=0.36。

原因は2つあった。ラベルが人間レビューなしの粗い代用だったこと。そして**写真の視点が間違っていた**こと。iPhoneを地面に直置きして撮ったので高さ0cm、しかも縦向き。実機のカメラは床から20cm・15°下向き・横長640×480。

誤検出源が「ティッシュ箱、壁紙、ノートPC画面、壁のメモ用紙」だったのが決定的だった。**レンズが床と同じ高さだと床がほとんど写らない**。画面の大半が壁と家具になる。

## 8/23 撮り直したら mAP 0.99 になった

視点を合わせて動画で撮り直した。20cmの高さに横向きで固定して15°下向き、画面の8割が床。5本、合計212秒。フレーム抽出して255枚。

そして255枚を**全部自分でラベル付けした**。ここは自動化できない。499個の矩形。ケーブルや靴だけが写っている4枚は空ラベルにした(負例として重要)。

結果:

| | 前回 | 今回 |
|---|---|---|
| precision | 0.374 | 0.979 |
| recall | 0.357 | 0.944 |
| mAP50 | 0.360 | **0.991** |

余談。labelImg 1.8.6 が矩形を描くたびにセグフォで落ちた。原因は新しいPyQt5との型互換で、drawRect/drawLineにfloatを渡すと拒否される。3箇所にint()を足して解決。2021年で更新が止まっているツールなので仕方ない。

## 8/24(午前) 0.99は嘘だった

嬉しくなったところで一度立ち止まった。**5本の動画から抽出したフレームを、ランダムに8:2で分割している**。同じ動画の別フレームは背景も配置もほぼ同じなので、valの画像はtrainとほぼ同一シーン。これは「一般化した」のではなく「見た絵を覚えた」だけかもしれない。

動画1本を丸ごとvalにする方式(Leave-One-Video-Out)で測り直した。

```
ランダム分割       mAP50 0.991
動画単位ホールドアウト  mAP50 0.845(平均)、最小 0.693
```

**0.146ポイントのリークが実在した**。ただし致命的ではない。1フォールドはval画像が1枚しかない(ほぼ静止した動画で重複排除された)ので信頼性が低く、それを除くと平均0.88。実用域と判断してmainにマージした。

どのみち実機のカメラで撮り直しとファインチューニングが要るので、ここで完璧を目指す意味は薄い。

## 8/24(午後) 単眼で距離を測る

ハード側の構成が Raspberry Pi 5 + Piカメラ(単眼)になった、という連絡が来た。深度が取れない。YOLOのBBox内の深度中央値で測距する設計が成立しなくなる。

対策として「対象は床に接している」という仮定を使う方式にした。カメラ高さhと下向き角θが分かっていれば、画像の縦位置から床上の距離が一意に決まる。実は**深度検出器でやっていた床面自己較正と同じ数式**なので、考え方はそのまま流用できた。

精度を計算してみたら性格がはっきりした。

| 真の距離 | h誤差±1cm | **θ誤差±1°** |
|---|---|---|
| 0.3 m | ±1.5 cm | ±1.1 cm |
| 1.0 m | ±5.0 cm | ±8.3 cm |
| 2.0 m | ±10 cm | **±30 cm** |

**近くは正確、遠くは壊滅的。支配的なのは取り付け角。** 1°ずれるだけで2m先が30cmずれる。

でも運用上は問題ない。遠くの検出は「あっちにゴミがある」と分かれば十分で、近づくたびに再検出されて精度が上がる。把持の直前(0.3m)なら±1〜2cmで、把持目標探索の許容±5cmに収まる。

ただし**接近中に目標を更新する仕組みが要る**。今までは最初に検出した座標を信じて走っていたが、それだと2m先の±30cmがそのまま接近位置の誤差になる。0.5m以内の新しい検出が来たら目標を更新する処理を入れた(別のゴミに乗り換えないよう距離ゲート必須)。

深度方式では発火回数0回。ブレないので更新の必要がない。「壊していない」ことの証明になった。

## 8/24(深夜) そしてカメラがOAK-D Liteに戻った

ハード側から連絡。**Raspberry Pi 5をやめて、カメラをOAK-D Liteにする**。ハードウェアステレオ深度がカメラ内で完結してPC負荷ゼロ、全デバイスをミニPCのUSBに直結。

つまり、今日の午後に作った単眼測距が**その日のうちに用済み**になった。

でも捨てない。OAK-D LiteはIRドットプロジェクタ非搭載なので、テクスチャのない床では深度が抜ける。**深度が取れなかったときのフォールバック**として残す。書いたコードが無駄になるかどうかは、だいたい後から決まる。

同時に渡された寸法で計算したら、こっちからも指摘が3つ出た。

1. **カメラの俯角25°だと、接近停止位置(x=0.33)でゴミが画角の下端ギリギリ**(50.1°、限界52°)。取付誤差1〜2°で消える。30°を推奨
2. **LiDARがアームを常時スキャンする**。LiDAR(x=-0.160)からアーム基部まで0.31m、伸ばすと0.51m。simで使っていたmin range 0.45では除去しきれない
3. アームの取付が主板上面 z=0.060 になり、**肩が11.5cm下がる**。可達範囲・接近オフセット・名前付きポーズ・把持姿勢が全部無効になるので測り直し

3周目の測り直し。まあ、実機に合わせるというのはそういうことだと思う。

## この期間の総括

**効いた修正**

1. **joint2のeffort訂正**(0.6→1.5 N·m)。実機のトルク計算を怠ったのが原因で、これ1つで統合検証が全滅していた
2. **接近を斜めにする**(0.33, 0.09)。アームが真正面を苦手とする幾何を認めた
3. **把持目標探索**。車体の停止精度に頼らず、到着後にアーム側で解ける点を探す
4. **時間制限つき自律ループ**。9時間待って1回失敗、を30分で3回試すに変えた
5. **視点を合わせた撮り直し**。mAP 0.36 → 0.99

**学んだこと**

- **物理量を計算せずに設定値を書かない。** effort=0.6は「実用0.6程度」というメモを何も考えずに全関節へコピーした結果で、必要トルクの45%だった
- **良すぎる数字は疑う。** mAP 0.99 はデータリークだった。動画単位で分割し直したら0.84
- **症状ではなく「回復しないもの」を探す。** RTFもAMCLも一時的に悪化して戻る中で、joint2だけが戻らなかった。それが答えだった
- **エージェントには時間予算と変更のホワイトリストを与える。** 「合格基準は絶対に触らせない」を明記すると、勝手に閾値を緩めて合格を作ることがなくなる
- **仕様は動く。** 単眼測距は作った日のうちに主役を降りた。それでもフォールバックとして残る道はある

**次**

肩が下がった新しい車体寸法で、可達範囲をもう一度測り直す。それが終われば接近オフセットと姿勢を決め直して、また6条件を通す。

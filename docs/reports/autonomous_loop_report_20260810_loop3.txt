================================================================================
根本原因の特定(追加の直接検証)
================================================================================
joint2が可動域上限(URDF: <limit lower="-1.65" upper="1.65" effort="0.6"
velocity="2.2"/>)と1ビットも違わず一致していたため、以下を直接検証した。

【検証1】armに手動でhome(全関節0)コマンドを送った
  結果: "Goal successfully reached!"(SUCCEEDED)と返るが、実際の
  joint2は1.65のまま全く動いていなかった。
  → arm_controller(joint_trajectory_controller)の設定
    (amr_controllers.yaml)に goal_tolerance / path_tolerance /
    constraints が一切定義されておらず、デフォルトでは目標時刻に
    達すれば実到達誤差を確認せずSUCCEEDEDを返すことを確認。
    これが「pick_and_place.pyのログは"successfully completed"と
    出るのに、実際にはarmが壊れた状態のまま」という不整合の直接の
    原因(検出漏れの原因)。

【検証2】コマンドの所要時間を2.5秒→8秒に伸ばして再送
  結果: 8秒与えても joint2 は 1.65 から1ミリラジアンも動かず。
  → 「速すぎて追従できない」という速度側の問題ではないと判明。

【検証3】joint2だけをわずか0.25rad(1.65→1.4)動かすコマンドを送信
  結果: これも全く動かず、正確に1.65のまま。
  → 極小の変位すら発生しないことから、緩やかな重力トルク不足による
    「じわじわ戻る」動きでもなく、完全な停止状態と判明。

【検証4】/check_state_validity サービスで、joint2=1.65
  (他関節≒0)の姿勢が自己干渉(self-collision)状態かを確認
  結果: valid: True(自己干渉なし)。
  → 見た目の干渉によるロックではないと判明。

【検証5】Grasp到達可能域全体(x=0.28〜0.36, y=0.02〜0.15格子)で
  compute_ikによりjoint2の値を走査
  結果: **どの到達可能点でも joint2 は 1.6250〜1.6495rad の範囲
  (可動域上限1.65からの余裕はわずか0.0005〜0.025rad)**。
  → Grasp姿勢(pitch=60°、これはホワイトリストで変更禁止)を満たす
    限り、joint2は原理的にほぼ必ず可動域限界のすぐそばに追い込まれる
    ことが判明。特定の(x,y,z)を避ければ回避できる問題ではない。

【結論】
joint2 の effort limit(0.6 N・m、xacro上で全関節共通の実機準拠値)が、
Grasp姿勢近傍でのjoint2の重力モーメントに対して不足しており、
一度その配置に到達すると物理的に(自己干渉ではなく純粋なトルク不足で)
そこから動けなくなる、という **URDF由来の実機物理制約の問題** である
可能性が最も高い。ソフトウェア側(再送、待機時間延長、段階的な動作)
では解消できないことを直接検証で確認済み。

【trash_2が異常に長時間化した理由(推定)】
trash_1のpick完了時点でjoint2が1.65に固着したまま次のpickシーケンスが
開始されている。pick_and_place.pyのsolve_ik()はself.current_joint_state
(ライブの現在関節状態)をIKシードとして使う実装になっており、
以前の別セッションでも「異常な関節配置(joint2=1.65)がIKシードとして
残ると、以降のcompute_ik診断が偽陰性を返す」ことが確認されている
(IKシード汚染)。trash_2のpickシーケンスもこの汚染された状態から
開始されており、Pre-grasp探索や降下経路の検証に通常よりはるかに長い
時間がかかった(あるいは実際にはIK自体は解けているが、汚染された
シードのために不安定な結果になっている)可能性が高い。今回はこの
仮説の追加検証までは時間内に実施できなかった。

================================================================================
終了条件の判断: C(ホワイトリスト外の変更が必要)
================================================================================
ステップ1の計測とステップ2の対策実装により、以下が確定した:
- ホワイトリスト内の対策(Pose Tracking簡略化、home復帰確認、応答
  セマンティクス修正)は全て実装・commit済みで、それぞれ意図通りに
  機能することを確認した。
- しかし根本原因である「joint2がGrasp姿勢近傍(可動域限界±0.001〜
  0.025radの範囲)に追い込まれ、effort limit(0.6N・m)不足のため
  物理的に home へ戻れなくなる」現象そのものは、これらのソフトウェア
  側対策では解消できないことを4種類の直接検証(通常送信/8秒送信/
  極小変位送信/自己干渉チェック)で確定的に示した。
- 考えられる本質的な対策は以下のいずれかだが、いずれも今回の
  ホワイトリスト範囲外である:
  1. joint2のeffort limitをURDF上で引き上げる
     → 「URDF寸法・可動域」の変更に該当する可能性が高く禁止
  2. Grasp姿勢(pitch=60°)がjoint2をほぼ確実に可動域限界へ追い込む
     という運動学的構造自体を、IK解探索の設計変更(例:
     avoid_collisions=Trueの有効化、異なるIK解ブランチの選好、
     Grasp姿勢に至る経路の再設計)で回避する
     → 今回のループの許可範囲(Pose Tracking/home確認/タイムアウト/
       AMCL tolerance)には含まれておらず、実装前に人間の承認が必要
  3. joint_trajectory_controllerにgoal_tolerance/path_toleranceを
     明示設定し、到達失敗を早期に検出してタイムアウトを待たずに
     リトライへ移行できるようにする(検出の迅速化であり、joint2の
     固着そのものの解決にはならないが、trash_2のような長時間ロス
     (120秒×2回)を防げる可能性がある)
     → controller設定の追加であり、今回のホワイトリストには明示
       されていないため、着手前に確認が必要と判断
以上より、指示に従いここでループを終了し、理由を明記して報告する。
